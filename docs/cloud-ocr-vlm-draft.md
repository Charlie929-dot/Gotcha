## 0. 一句话

把「窗口截图」直接交给云端多模态模型（VLM），一次调用同时拿到**文字 + 理解**，替代当前纯本地的 WinRT OCR。

代价是：**屏幕像素（而不只是脱敏后的文本）将离开本机**，这与现有安全前提直接冲突，所以必须先拍板、后动手。

## 1. 现状与证据（为什么想换）

| 事实 | 证据 |
| - | - |
| 本地 WinRT OCR 在真实屏幕小字号下不准 | 2026-10-21 实测：同一张真实截图，15 个关键词命中 **11/15**（漏「项目计划」「完成采集管线验收」「orb」「窗口标题」） |
| 不换引擎也能改善 | 同一截图放大 2×（双三次）后 **15/15**，耗时 118ms（原生 250ms） |
| 本地 OCR 不产出语义 | 只回文字；M2 的归纳/连边仍要按 D5 再走一次云端（对文本） |
| 云端 VLM 预期更准 | **推测，未实测**：主流 VLM 对 UI 截图文字识别通常显著优于轻量 OCR，且能直接给摘要/分类。本轮未出网验证，属待验证假设 |

> 结论：这不是「本地 OCR 不够用」的补丁，而是**换数据边界**的架构选择。若只是想让本地 OCR 更准，2× 放大就够（另案，可独立做）。

## 3. 三种接入形态（先选形态，再谈实现）

### A. 影子对比（推荐第一步，零隐私风险）
本地 OCR 照常写库；另开一个**手动触发**的对比任务：拿 `.tmp/` 里已有的截图样本（或 `capture.save_shots=1` 落盘的图），云端跑一遍，产出「本地 vs 云端」逐帧对比表。

- 收益：先量化云端到底强多少（现在只有推测），再决定要不要改架构
- 风险：样本仍会出网 → 需先批准 + 只用手工挑的、确认不含敏感信息的样本
- 工时：0.5 天（脚本 + 报告）

### B. 云端主识别 + 本地兜底（形态最激进）
每次变化帧先送云端；超时/失败/离线/熔断 → 回落本地 OCR。

- 收益：准确率 + 语义一步到位；本地 CPU 反而下降
- 成本：全量上传，费用与隐私暴露面最大
- 工时：2–3 天（含降级、熔断、迁移、开关）

### C. 按需理解（M2 形态）
日常只存本地 OCR；用户发问/生成归纳时，才把相关帧送云端。

- 收益：暴露面最小（只传被问到的帧），仍然能拿到高质量理解
- 代价：M1a 内不能验证「实时理解」体验
- 工时：M2 再说

## 4. 隐私设计（若批准，以下为不可协商项）

1. **只传窗口截图**：沿用现有窗口裁剪，不含任务栏、不含其他窗口、不含桌面背景。
2. **上传门（新增第 4 层）**：满足任一条件即**不上传**，只走本地 OCR——
   - 命中第 2 层黑名单进程（密码管理器/网银/隐私窗口）；
   - 本地 OCR 结果命中 `sensitive=1` 规则；
   - 用户手动标记「不记录」的时段（D6 总开关）。
3. **上传前确定性披露**：设置页有「查看即将上传的内容」预览（最近 5 帧缩略图 + 是否会被上传 + 原因），默认开启预览而非直传。
4. **不落盘不缓存**：图片只在内存中转成请求体，不写额外临时文件（现有 `tmp/frame-*.png` 用完即删）。
5. **调用留痕**：本地记录 `ts / bytes / sha256 / model / ms / ok`，**不记原文、不记响应体**（与 `security.md` 日志规则一致）。
6. **供应商约束**：必须选支持零留存/no-train 条款的 API 与端点（Q7）。
7. **预算闸**：每日上传张数与字节上限，超限自动降回本地并记 `cloud_budget_exceeded`。

## 5. 密钥（与「不做密钥管理」边界的处理）

| 方案 | 做法 | 与 D2 的关系 |
| - | - | - |
| K1（推荐） | `GOTCHA_VLM_API_KEY` 环境变量 / `.env`（已在 `.gitignore`）；UI 只显示后 4 位 | 与现有 `DEEPSEEK_API_KEY` 一致，不改边界 |
| K2 | Windows 凭据管理器（DPAPI）存 key，设置页录入 | 需要拍板：这是「配置」还是「密钥管理功能」 |
| K3 | 内置共享 key | **否决**：等于把 key 分发给所有使用者，也会落到仓库 |

明确不做：多 key 轮换池、代理转发、key 共享。

## 6. 成本与延迟（估算，价格项未查证）

- 频率假设：帧差过滤后每 2–3 分钟 1 帧 → 8 小时约 **160–240 帧/天**，取 200。
- 图片 token 粗估：长边压到 1568（约 1200×750）≈ **1100–1500 tokens/帧** → 约 **25–30 万 tokens/天**、**700–900 万 tokens/月**。
- 单价：**未查证（本轮未出网报价）**，需按选定模型实价折算；拍板前给不出人民币价目，只能给量级。
- 延迟：推测 1–3s/帧（未实测）；本地 OCR 为 0.1–0.7s。→ 必须异步队列 + 背压（现队列上限 50 可直接复用）。
- CPU：云端路线下本地只做帧差 + 编码，A2 的 CPU 占用大概率下降。

## 7. 失败与降级

- 超时 8s；连续 3 次失败 → 熔断 10 分钟回本地；熔断期间不重试。
- 断网：直接本地 OCR，不排队重放（避免恢复后批量补传）。
- 结果标记 `ocr_source = 'local' | 'cloud'`，便于对账与回放；`events` 表加列走 **v2 迁移**（与 nodes/edges 同批）。

## 8. 验收口径变化（M1a 出口标准要不要改）

| 项 | 现状 | 若走云端 |
| - | - | - |
| A1「昨天下午三点在干嘛」 | 时间+应用+标题+OCR 摘要 | 不变，且摘要质量更高 |
| A2 CPU < 3% | 本地 OCR 为主要开销 | 应更容易达标；需新增「上传字节/张数」指标 |
| A5 埋点 | frames/ocr_runs/queue_dropped/errors | 增加 `uploads`/`upload_bytes`/`cloud_failures`/`budget_exceeded` |
| **新增 A6（建议）** | — | 隐私红线：敏感帧上传 **0 次**；日志 **0** 条原文；熔断可复现 |

## 9. 分期与工时（形态 A → B）

1. **第 0 步（0.5 天）**：影子对比脚本，仅用手工挑选的非敏感样本，产出准确率/耗时/单价实测报告 → 用数据回答「值不值得」。
2. **第 1 步（1 天）**：接入层（一个统一 `VlmOcrEngine` 实现 `OcrEngine` 接口）+ 上传门 + 预算闸 + 熔断，默认关闭。
3. **第 2 步（0.5 天）**：v2 迁移加 `ocr_source`；设置页开关与预览。
4. **第 3 步（观测 3–7 天）**：成本、准确率、误上传事件核对，再决定默认值。

## 12. 我作为执行方的立场（供拍板参考）

- 技术上可行，收益大概率真实（**未实测，别当结论**）。
- 但这是本项目至今**唯一一次让原始屏幕数据出本机**的改动，建议按「形态 A 影子对比 → 用数据决定 → 再考虑形态 B」推进，不要一步到位。
- 如果只用本地方案：2× 放大已经把本轮实测从 11/15 提到 15/15，M1a 的 A1 验收完全够用；云端的主要增量价值在 M2 的**理解**，不在 M1a 的**转录**。
