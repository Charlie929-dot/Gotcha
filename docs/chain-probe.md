# 信息链探针：窗口切分与 UIA 覆盖率（一次性验证）

> 2026-10-25 起，对应 `docs/information-chain-direction.md` 待拍板清单第 3、5 项：
> **焦点窗口占用段怎么切**、**UIA 最小闭环与 OCR 兜底边界**。
> 结论未拍板前不动 schema、不开 `src/chain/`；这份文档只负责「先拿数据」。

## 0. 这是什么

三个一次性脚本，回答两个问题：

| 问题 | 脚本 | 输出 |
| - | - | - |
| 前台窗口占用段怎么切才不碎、不吞 | `scripts/chain-probe/collect.ps1` + `analyze.mts` | 采集 JSONL + 切分对比报告 |
| UIA 能拿到多少文本、哪些窗口拿不到 | `scripts/chain-probe/uia-probe.ps1` | UIA 覆盖 JSONL + 同一份报告第 3 节 |

它们**不进主程序**、**不碰应用数据库**、**不出网**。分析器是纯函数 + 本地文件读取，可以单测。

## 1. 跑法

```powershell
# 采集（另开一个窗口，正常用电脑；至少 20 分钟才有统计意义）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/chain-probe/collect.ps1 -Minutes 30

# UIA 覆盖率（快照当前所有可见窗口，一分钟出结果）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts/chain-probe/uia-probe.ps1 -Once

# 出报告
npm run chain-probe -- .tmp/chain-probe/collect-<时间>.jsonl --uia .tmp/chain-probe/uia-<时间>.jsonl
```

常用开关：

| 开关 | 作用 |
| - | - |
| `collect.ps1 -Seconds 20` | 短样本自测（比率类指标不可当真） |
| `collect.ps1 -NoTitles` | 不记窗口标题（切段会退化成「只看进程」） |
| `collect.ps1 -MoveStepPx 8` | 鼠标移动抽稀更狠，事件更少 |
| `collect.ps1 -IdleSeconds 120` | 多久不动算空闲 |
| `uia-probe.ps1 -Minutes 15` | 连续盯前台窗口采样（每个新窗口只测一次） |
| `uia-probe.ps1 -TimeoutSeconds 5` | 单窗口 UIA 超时（默认 10s） |
| `analyze.mts --json` / `--out report.md` | 机器可读输出 / 落文件 |

## 2. 记录什么，不记录什么

记录：

- 前台窗口变化：时刻、hwnd、pid、进程名、标题、窗口矩形；
- 标题变化（同一窗口内，用于判断「同应用跳转要不要切段」）；
- 鼠标移动（按像素步长抽稀）、左 / 右 / 中键按下、滚轮、空闲 / 返回；
- UIA 每窗口的**统计**：元素数、有名字的元素数、名字总字符数、密码控件数、耗时、是否超时。

不记录：

- **键盘**（脚本里没有键盘钩子，这是硬边界）；
- 屏幕内容、截图、OCR 文本、剪贴板、URL、页面正文；
- UIA 的**文本本身**——只落字符数，用来算覆盖率。

输出全部在 `.tmp/chain-probe/`（`.tmp/` 已在 `.gitignore`），不提交。标题仍然属于内容，介意时用 `-NoTitles`。

## 3. 报告怎么看

### 3.1 窗口占用段：四种切法对比

同一份数据按四种规则切，比的是「哪种切法一段能承载足够内容」：

| 规则 | 含义 |
| - | - |
| `raw` | 每次前台切换就切（最碎的基准） |
| `window` | 进程 + 标题当身份；标题变化即切；空闲 >60s 断开 |
| `app` | 只按进程身份，忽略标题；空闲 >60s 断开 |
| `app-loose` | 只按进程身份；空闲 >5min 才断开 |

判读标准（不是验收线，是「够不够用」的直觉）：

- 中位时长在**分钟级**、`<5s` 占比低 → 这段能承载摘要、双链和证据截图；
- `<5s` 占三成以上 → 这个规则会把一段真实经历切碎；
- `app` 的段数明显少于 `window` → 标题更适合当**段内属性**，而不是段的身份。

### 3.2 截图触发密度

按「事件点」口径估算：左 / 右 / 中键点击、滚轮、以及「移动 ≥40px 后静止 ≥400ms」，同一次触发 2s 内去重。

报告给三个数：触发点/小时、每段触发数中位、**没有任何触发的段**占比。

- 触发过密（>300/小时）→ 截图存储与 AI 核验都会被拖重，要加冷却或只在内容变化时截；
- 触发过疏（<20/小时）→ 回查时找不到对应那一帧，「精确核验」落空；
- 无触发的段 → 这段没有证据截图，AI 只能靠内容判断。

### 3.3 UIA 覆盖率

按文本量分三档：`0`（拿不到）、`<200 字`（很薄，多半只有外层控件）、`≥200 字`（够用）。

- 无文本窗口 → OCR 兜底不是可选项；
- 有文本但很薄 → UIA 只拿到了标题栏一类，正文仍需 OCR 或另找路径；
- 单窗口耗时中位数偏高（>1s）→ 采集侧要做超时与降级，不能串行等。

## 4. 已知限制（先记下来，别拿它当结论）

1. **样本时长决定可信度**：比率类指标（段/小时、触发/小时）在 20 分钟以下只能看趋势。
2. **Electron / Chromium 的 UIA 树依赖可访问性开关**：Chromium 只在检测到辅助技术或启动参数带 `--force-renderer-accessibility` 时才完整暴露 UIA。本机实测 DSH（Electron）能拿到 4000+ 元素，但这不代表所有 Chromium 应用默认如此，换机器要重测。
3. **单窗口 4000 元素截断**：超过就标 `truncated`，字符数是下限不是上限。
4. **无击键信号**：打字停顿时机拿不到，只能靠鼠标与窗口变化推断（键盘钩子按隐私边界不做）。
5. **鼠标坐标是物理像素**：高 DPI 混合缩放时不同显示器之间不可直接比较。
6. **窗口矩形来自 `GetWindowRect`**：比 DWM 可见边界各多 8px（见 gotchas「截图裁剪只取可见窗口」），只用于判断「窗口是否变化」，不用于裁剪。
7. **UIA 可能挂住**：每个窗口在独立子进程里测，父进程 10s 强杀；被杀记为 `timedOut`，不算失败也不算成功。

## 5. 本轮实测（2026-10-25）

见下方「实测记录」小节；每次重跑把新的汇总数字追加到这里，不覆盖旧记录。

### 实测记录

**轮次 1（2026-10-25 22:46–23:09，22m32s，单窗口为主的阅读会话）**

采集：2531 条记录、0 坏行；前台切换 5 次（13.3/小时）、标题变化 1 次、空闲占 **45.3%**（10m13s，6 段空闲）。

| 规则 | 段数 | 中位 | P90 | 最长 | <5s 占比 |
| - | -: | -: | -: | -: | -: |
| raw（每次切换都切） | 6 | 2m40s | 9m07s | 9m07s | 33.3% |
| window（进程+标题，空闲>60s 断开） | 11 | 1m00s | 1m31s | 6m02s | 36.4% |
| app（忽略标题，空闲>60s 断开） | 10 | 1m00s | 1m31s | 6m02s | 30.0% |
| app-loose（空闲>5min 才断开） | 10 | 1m00s | 1m31s | 6m02s | 30.0% |

触发点：38 个（101.2/小时）；原始点击 42、滚轮 163、移动后暂停 7（2s 冷却后剩 38）。**每段触发数中位 0，11 段里有 6 段（54.5%）完全没有触发点。**

UIA：连续采样探测 3 个窗口全部成功——firefox 23 441 / 11 004 字符（7 938 元素，超出 4 000 扫描上限）、dsh next 79 114 字符（4 463 元素），单窗口中位耗时 **1 420ms**。另有一次全可见窗口快照（6 个窗口）：`workbuddy` 1 个元素 / 0 字符、`applicationframehost`（UWP 宿主）0 元素，其余 4 个有文本。

判读与局限（照实说）：

1. **这轮样本不够定切分规则**：22 分钟只切了 5 次前台，几乎全程一个窗口，四种规则的差异被压缩了。要定「窗口段」必须再跑一轮**多应用来回切**的真实工作（浏览器查资料 + 编辑器 + 聊天），至少 40 分钟。
2. **空闲占 45% 不是噪声**：离开时窗口不变、但「占用」不应继续累计。空闲断段这条规则必须有，阈值（60s？ 5min？）还得靠更长样本定。
3. **标题几乎不影响段数**（11 vs 10）：这轮里标题变化只 1 次。窗口标题适合作段内属性，但样本太薄，不能当结论。
4. **一半的段没有证据截图**：按 2s 冷却后，轮询式「移动后暂停」几乎不触发（7 次），触发主要来自点击与滚轮。如果要求「每段都能定位到某一帧」，现在的触发口径不够；要不要为长段补一张代表帧，另议（`D32` 的代表帧思路可复用）。
5. **UIA 覆盖率是「应用相关」而不是「平均 60%」**：Chromium 系（firefox / dsh）能拿到上万字符，但 UWP 宿主与部分应用 0 元素。单窗口 1.4s 的耗时也意味着**不能串行等 UIA**——超时 + 降级到 OCR 是必须的。

原始 JSONL 只在 `.tmp/chain-probe/`，不入库。

**轮次 2（2026-10-25 23:28–23:34，5m04s，刻意高频切换 9 个应用）**

采集：4722 条记录、0 坏行；前台切换 **36 次（426.4/小时）**、标题变化 11 次；末尾有 1 段空闲（采样即结束，时长未知，报告会单独标出）。

| 规则 | 段数 | 中位 | P90 | 最长 | <5s 占比 |
| - | -: | -: | -: | -: | -: |
| raw（每次切换都切） | 38 | 1s | 12s | 2m03s | 71.1% |
| window（进程+标题） | 38 | 1s | 12s | 2m03s | 71.1% |
| app（忽略标题） | 23 | 2s | 23s | 2m03s | 60.9% |

触发点：66 个（781.7/小时）；点击 130、滚轮 293、移动后暂停 11（2s 冷却后剩 66）。**38 段里有 17 段（44.7%）没有触发点。**

UIA：15 个窗口全部探测成功，11 个 ≥200 字、4 个很薄，单窗口中位 **823ms**：

| 应用 | 文本字符 | 元素数 | 耗时 |
| - | -: | -: | -: |
| firefox（5 个窗口） | 10 615–11 027 | 7 873–7 960 | 2.0–4.1s |
| dsh next | 13 121 | 518 | 239ms |
| pdfeditor | 2 134 | 305 | 688–1 484ms |
| explorer | 346 | 34 | 198ms |
| pdflauncher | 777 / 1 243 | 90 / 218 | 416 / 990ms |
| windowsterminal | **90** | 16 | 176ms |
| workbuddy | **20** | 2 | 272ms |
| opencode | **16** | 13 | 823ms |
| weixin（微信） | **6** | 1 | 134ms |

判读：

1. **两种样本差 30 倍**：轮次 1 是 13 次切换/小时（纯阅读），轮次 2 是 426 次/小时（刻意的极端切法）。真实工作日大概落在中间，**切段规则必须两头都能看**——用 5 分钟极端样本定阈值会把规则调得过松。
2. **极端切法下 71% 的段 <5s**：这不是「标题切碎」的问题，是切窗口本身太碎。结论：切段规则需要「合并短暂的一瞥」这一步（例如 <3s 的段并进前一段），否则每切一次就落一个球。
3. **微信 / 终端 / opencode / workbuddy 的 UIA 只有个位数到几十个字符**：这些正是自绘或非标准控件面板。**OCR 兜底不是边缘情况**，对这几类应用它就是主路径。
4. **浏览器 UIA 很重**：firefox 近 8 千元素、单次 2–4 秒。采集侧必须「异步 + 上限 + 超时」，不能放在会阻塞采集的路径上。
5. **没有触发点的段占 44.7%**：高频使用下依然如此（因为 2s 冷却把连续滚轮合并了）。要么降低冷却，要么给长段补一张代表帧。
6. **5 分钟样本能回答的和不能回答的**：机制、极端碎片度、每应用 UIA 覆盖——够；空闲阈值、正常中位时长、真实触发密度——不够，仍需 20–40 分钟的正常工作日样本。


## 6. 跑完之后

数据只回答「能不能」，不替拍板人决定。两个问题的产出应该长这样：

- 窗口段切分：给出**一条**推荐规则（含空闲阈值、标题是否参与身份），以及它在真实数据上的中位时长与碎段占比；
- UIA：给出**一条**兜底边界（哪些窗口直接走 OCR、哪些先用 UIA），以及单窗口耗时的量级。

这两条定下来之后，才写信息链契约与 `src/chain/` 的第一版。
