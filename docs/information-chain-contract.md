## 0. 一句话

**一段记忆 = 一个窗口的一段焦点占用；段内的事件点触发截图作为证据；内容是 UIA 优先、OCR 兜底的文本流；标签与双链是可重建的派生，随时可以推翻重算。**

## 1. 三个契约（立不住，后面全部返工）

1. **一段到底包含什么**：段的边界、身份、有效时长怎么算。
2. **事件 / 内容 / 截图怎么互指**：用稳定 id，不靠时间戳猜。
3. **哪些不可变、哪些可重建**：证据只写一次，理解随便改。

## 2. 实体与字段

命名统一 `chain_` 前缀，与旧表并存，不迁移旧数据（D38）。

### 2.1 段 `chain_segment`

```sql
CREATE TABLE chain_segment (
  id          INTEGER PRIMARY KEY,
  start_ts    INTEGER NOT NULL,   -- 首次成为焦点
  end_ts      INTEGER NOT NULL,   -- 最后一次焦点结束（含接续后的跨度）
  active_ms   INTEGER NOT NULL,   -- 有效占用：排除空闲
  idle_ms     INTEGER NOT NULL,   -- 段内被排除的空闲（接续造成）
  day_key     TEXT    NOT NULL,   -- 本地日期 yyyy-mm-dd，按 start_ts 归日
  app         TEXT,               -- active-win 的 owner.name
  exe         TEXT,               -- 进程名，小写
  pid         INTEGER,
  hwnd        INTEGER,
  title_first TEXT,               -- 段开始时的标题
  title_last  TEXT,               -- 段结束时的标题
  created_at  INTEGER NOT NULL,
  closed      INTEGER NOT NULL DEFAULT 0   -- 0=还开着，1=已收口
);
```

- **身份**：`pid + hwnd`（同窗口内标题变化算换一件事，见下）。`hwnd` 是窗口句柄，`pid + title` 不够：同一进程的多个窗口可能同标题。
- **标题抖动抑制**：标题在 3 秒内变回原值则不切段（实测见过 1 秒内的 A→B→A，见 `docs/chain-probe.md`）。未读计数、播放进度这类会持续变的标题，抑制窗口内不产生新段。
- **边界**：焦点切走即切段；空闲 >60s 断开；**走开又回到同一窗口就接续**（D39），接续上限 30 分钟。
- **段身份以动作为准**（v0.13）：点击 / 滚轮在**事件坐标**上查 `WindowFromPoint` → 根窗，作为该次动作所属的窗；键盘 / 没有动作时用前台事件兜底。理由：前台是「键盘路由目标」，程序可抢（火绒升级器的 0×0 窗抢了 52 秒），点中的窗才是用户真正在操作的。**不用光标当前位置**做身份——人停手时光标常停在任务栏上（实测 60 秒里 22 次）。
- **幽灵前台窗不成段**（v0.12）：窗口事实满足任一条就不当一段——`visible === false`、`minimized === true`、窗口矩形与**所在显示器**的交集 < 32×32 px、窗口类名属系统覆盖层或桌面外壳（`TaskSwitcherWnd` / `MultitaskingViewFrame` / `ForegroundStaging` / `Shell_TrayWnd` / `Shell_SecondaryTrayWnd` / `Progman` / `WorkerW`）。丢弃方式：不切段、不收口、不动标题抖动窗口，**输入继续算在当前开着的段上**；当前没段就留空（宁可时间轴有洞，也不记到错窗口上）。字段是**可选事实**——源没报就按「未知」放行，绝不猜默认值。
- **时长**：`active_ms` 是有效占用，`end_ts - start_ts` 是跨度；两者不等时差额就是 `idle_ms`。
- **不变量**：任意时刻最多一个段在占用；段与段不重叠。

#### 2.1.1 段行的两期落定（v0.4 敲定，见 D40）

段的结束时刻在开段时不可能知道，而子行（事件 / 截图 / 内容）**必须立刻拿到 `segment_id`**。两条路：

| 方案 | 代价 |
| - | - |
| 收口时再插段，子行先缓冲在内存 | 段可能长达数小时；崩溃时整段证据全丢，截图文件变孤儿 |
| **开段即插、收口落定（采用）** | 段行有一段时间是「未收口」状态，需要 `closed` 标记与启动收尾 |

- 开段：插入一行，`closed=0`，`end_ts` 暂等于 `start_ts`、`active_ms=0`、`idle_ms=0`。
- 收口：**唯一一次** UPDATE，落定 `end_ts` / `active_ms` / `idle_ms` / `title_last` / `closed=1`；此后这些字段永不改。
- 未收口的段 **`end_ts` 是暂定值**，所以按时间查段时对 `closed=0` 的段只看 `start_ts`，不拿结束时间去卡。
- 启动时把上次异常退出留下的 `closed=0` 段按「最后一个子行时刻」收口（`finalizeAbandonedSegments`）。崩溃时真实结束时刻已不可知，所以 `idle_ms` 记 0，不编造。
- 写入端保证：开段前没有别的开段、且不与上一个收口段重叠；收口前校验所有子行都 ≤ `end_ts`。

### 2.2 事件 `chain_event`

```sql
CREATE TABLE chain_event (
  id         INTEGER PRIMARY KEY,
  segment_id INTEGER NOT NULL,    -- 属于且仅属于一个段
  ts         INTEGER NOT NULL,
  kind       TEXT    NOT NULL,    -- click_left / click_right / click_middle / wheel / move_pause / typing / enter
  x          INTEGER,             -- 屏幕物理像素（wheel / click / move_pause 有效）
  y          INTEGER,
  delta      INTEGER              -- wheel 的方向与格数
);
```

- **事件不是图谱节点**，不上画布，只作段内时间锚点与截图触发器（D39 / 方向文档）。
- **呈现口径**（v0.12）：时间轴 / 画布 / 问记忆**只呈现有证据的点**（有截图或有内容）；事件是触发与统计的原料（段时长、空闲、打字、派生），留在库里，但不进产品界面。
- `enter` = 段开始时的入场事件（保证每段至少有一个锚点）。
- `move_pause` = 移动 ≥40px 后静止 ≥400ms（探针口径，可调）。
- `typing` = 键盘输入停顿满 3s 的那一刻（v0.4 新增；不含任何按键内容）。
- **事件一律落行，截图冷却只决定要不要顺手截一张**（v0.4）：切过来 1 秒内点的那一下，事件锚点必须留下，不能因为撞上冷却就整条丢。
- **滚轮的手势合并交给传输层**：钩子把同一次滚动手势（间隔 <500ms）累加成一条 `wheel` 再喂进来；段机不负责合并，否则采集粒度被绑死在核心里。

### 2.3 截图 `chain_shot`

```sql
CREATE TABLE chain_shot (
  id         INTEGER PRIMARY KEY,
  segment_id INTEGER NOT NULL,
  event_id   INTEGER,             -- 触发它的那个事件
  ts         INTEGER NOT NULL,
  path       TEXT,                -- 文件路径；剪载荷时置空，行不删
  width      INTEGER,
  height     INTEGER,
  bytes      INTEGER,
  source     TEXT NOT NULL,       -- event / enter / typing
  tier       TEXT NOT NULL,       -- hot / warm / cold（归档层，见 §5）
  container  TEXT                 -- 归档容器路径；hot 为空
);
```

- 「只写一次，不覆盖」；截图是「AI 命中后回来核验」的最终证据。
- **来源（v0.5，D42）**：事件到了**现抓一帧**（不用采集管线 ≤2s 的旧帧）；抓帧是异步的，`ts` 仍是触发事件的时刻——证据时刻不因抓图慢而漂。
- **什么时候拍（v0.11，2026-10-27 拍板）**：只由三类时刻驱动——① 左 / 右键**从 ≥ `captureCooldownMs`（2s）的静默里**发起 → 立刻拍；② **打字被点击 / 滚轮打断** → 立刻拍（保住刚敲进去的内容，这一拍**不要求静默**，只守 2s 最小间隔）；③ **滚轮手势停下 2s** → 拍滚动结果（这 2s 内来了别的输入就作废）。**鼠标移动永不拍**（只记 `move_pause` 事件）；**打字自己停顿也不拍**（只补 `typing` 事件）。事件本身一条不丢：触发规则只决定 `capture` 真假。入场帧每段一张，受最小间隔约束。理由：旧口径（2s 冷却 + 每个事件都算触发）实测 41 分钟 291 张 / 175 MB，且每张 500ms 压在主线程——用户按着鼠标拖动会明显顿。
- **抓帧前后各校验一次窗口身份**（v0.5）：`pid + hwnd` 与段不一致就丢弃这一帧。拍的是「这扇窗所在的屏幕区域」，抓帧要 100–300ms；这期间前台被别的窗口盖住，拍到的就是别人的画面（真机实测踩到过）。**错证据比没证据更糟**，所以宁可丢。
- **文件位置**：`<userData>/chain-shots/<YYYY-MM-DD>/s<段>-e<事件>-<ts>.jpg`；临时帧写 `<userData>/tmp-chain/`（与旧管线的 `tmp/` 分开，免得被启动清理误删）。cold / archive 的图在 `<userData>/chain-shots/archive/<日期>-<层>.cgar` 容器里，行里 `path` 置空、`container` 指向容器。
- **格式是 JPEG**（v0.7，D44）：采集即编码 **q85**。**两份图一次抓帧出**（v0.11）：证据图 = 原生像素、宽 ≤1920、**在隐藏渲染进程里直接编码成 JPEG**（`format: 'jpeg'`），主进程只写字节；同一帧另出一张 **2× PNG** 给内容车道的 OCR 兜底（UIA 文本 < 200 字符时用），读完即删。以前是「2× PNG 落盘 → 主进程 `nativeImage` 解码 → 缩到 1920 → 重编码 JPEG」，整张压在主线程上。**WebP 仍没有编码器**（Electron `nativeImage` 只支持 PNG / JPEG；不为此加依赖），契约原写的「hot = WebP」按实测改成 JPEG q85——如实记为偏差，不是静默降级。
- 入场帧：段开始时默认截一张，`source='enter'`。
- `typing`：键盘停顿补的**事件**（v0.11 起不再配图），`source='typing'` 只对历史行有意义。
- **每张截图都挂在触发它的那个事件上**（v0.4）：入场帧挂 `enter` 事件，打字帧挂 `typing` 事件。这样「点开一张图 → 看它在段里的位置」没有例外分支；`event_id` 为空只作为防御态存在。
- `sensitive=1` 的段不存图（对齐 D10 / D19）。
- 分级保留见 §5：任何归档都必须保留 `shot.id → 事件 / 段` 的映射，解出后能回到原来那一刻。
- **过期不删行**：保留期只重编码 / 打包，改 `tier` / `container` / `path` / `bytes` / `width` / `height`（v0.7，D44），`id` 与挂载关系永不删（对齐 D32 的「剪载荷不剪 id」）。

### 2.4 内容 `chain_content`

```sql
CREATE TABLE chain_content (
  id          INTEGER PRIMARY KEY,
  segment_id  INTEGER NOT NULL,
  captured_at INTEGER NOT NULL,
  source      TEXT NOT NULL,      -- uia / ocr / manual
  text        TEXT NOT NULL,
  chars       INTEGER NOT NULL,
  hash        TEXT NOT NULL       -- 去空白后的指纹，用于判重与变化率
);
```

- 一段可以有多条（随时间增长），**每条都带来源**，不许把 UIA 与 OCR 混成无来源的一坨。
- UIA 拿不到（实测微信 6 字符、终端 90 字符）才走 OCR；两者都失败就留空并标记，不编造。
- **同段内与上一条指纹相同的正文不重复落行**（v0.4）：正文没变就说明没有新信息，多存一条只是备份。指纹 = 去空白后的 sha256 前 16 位，只看内容不看排版。

**采文本的时机与口径（v0.6，D43）**：

- **抓帧落定后异步读一次**，**不占抓帧队列**：抓帧冷却 2s、UIA 单次 0.8–4s，混进同一个串行队列会让后面每张证据都晚到，晚到的帧前台早已切走 → 证据被身份校验丢掉。证据优先，内容随后。
- **同段 15s 节流**：两次读数至少间隔 15s（按**尝试**时刻算，读失败也占一个窗口，免得坏窗口每张图都重试）；换段后第一次必读。
- **UIA 优先、OCR 兜底**：UIA 文本 < **200 字符**就当没拿到（自绘窗口的树就是这么薄），走 OCR；OCR 读**这次抓帧的那张图**，不为读文字额外再截一张。
- **UIA 的实现**：长驻 PowerShell worker（`resources/chain/uia-text.ps1`，行式 JSON）；单次**超时 3s，超时即杀子进程**并进入 5s 重启冷却（UIA 可能永久挂住，只拒请求不杀进程会让后续请求排死）；扫描上限 **4000 元素**、单条文本上限 **100k 字符**，超了标 `truncated`（不静默）；`IsPassword` 控件**一个字符都不取**；输入框正文另从 `ValuePattern` 取（仅 `Edit` 控件）。
- **写回按段 id**：内容读取比抓帧慢，读回来时段可能已经收口；写回**触发那一刻的那一段**，不写进当前开着的段（`ChainRecorder.recordContentFor`）。时刻用触发事件的时刻（与截图一致）。
- **黑名单窗口不截图 → 也就没有内容**：内容由截图触发，隐私红线（密码管理器等）在截图那一步已经拦掉。

### 2.5 派生层（可重建）

```sql
CREATE TABLE chain_tag          (id INTEGER PRIMARY KEY, segment_id INTEGER, name TEXT, source TEXT);
CREATE TABLE chain_link         (id INTEGER PRIMARY KEY, name TEXT UNIQUE, aliases TEXT);  -- aliases = JSON 数组
CREATE TABLE chain_link_segment (link_id INTEGER, segment_id INTEGER, weight REAL, PRIMARY KEY (link_id, segment_id));
CREATE TABLE chain_vector       (segment_id INTEGER PRIMARY KEY, model TEXT, dim INTEGER, vec BLOB, text_hash TEXT,
                                 content_max_id INTEGER);  -- v0.8：建向量时的内容水位
CREATE TABLE chain_derive       (segment_id INTEGER PRIMARY KEY, text_hash TEXT, content_max_id INTEGER,
                                 derived_at INTEGER);      -- v0.8：这一段这个指纹抽过标签 / 双链了
```

- 标签、双链、向量、摘要、命名**全部可重建**：删掉能从 `chain_content` 重算；`chain_derive` 也是派生账，一起删（删了就重抽一遍）。
- 双链是**多对多**（方向文档的「双链球可以指向多个窗口」）。
- **生成规则（v0.8，D45）**：每段收口后先由 LLM 抽一次 `{tags, links}`（标签 2–5 个、双链 ≤8 个；硬上限 8 / 10，超长截断而不是整条丢）。然后名字与**已有名字**做本地语义比对并合并：
  - **相似度 ≥ 0.95**：直接复用已有写法，不问模型；
  - **0.90–0.95**：模糊带，攒成一批问模型「是不是同一个概念 / 实体」，判同才复用；
  - **< 0.90**：新建。
  - 复用时写法不同（「记忆系统设计」↔「记忆系统」）记进 `chain_link.aliases`；`chain_link_segment.weight` 暂统一 **1.0**（出现即关联，权重语义以后有需要再定）。
  - 相似度 = 两个名字各自过本地 `bge-small-zh-v1.5`（512 维）后的余弦；**精确同名 / 别名命中不花模型**。合并只影响「这一段的标签叫法 / 挂到哪条双链」，不删 `chain_link`（别的段还在用）。
- **送模型前的正文整理**：`chain_content` 是 UIA 整窗树 + OCR 的叠加，同一段里会攒下多份几乎相同的文本。派生时先**按行去重**（保留第一次出现的顺序）、空白归一、**上限 6000 字**（超了截断并标 `truncated`）。指纹算在**截断后**的正文上：上限之外的滚动不触发重抽，上限之内的变化才重抽。实测一段 UIA 整窗 21 409 字 → 去重后 6 000 字（丢掉 80 行重复），OCR 段基本不变。
- **幂等 / 水位**：`chain_vector.text_hash`、`chain_derive.text_hash` 记「这个指纹算过了」；`content_max_id` 是更便宜的判据——又读回来一条内容（`MAX(chain_content.id)` 变大）才重新看指纹，指纹没变就只推水位、不花 token。重抽时**整段替换**该段的 `chain_tag` / `chain_link_segment` 行。
- **出网门与预算**：复用 **D24 一次性确认**（`graph.outbound_consent`）与 **D22 每日预算**（`graph.budget_tokens_per_day`，与图谱共用同一份日账 `graph.usage.<day>`）；确认文案覆盖「信息链段内文本也会脱敏后发往供应商」。未确认 / 缺 key / 超预算时**只建本地向量**，抽取留在待办里，下次开始采集再补（不静默假装抽过）。载荷仍由 `understand/cloud/redact.ts` 唯一出口产出（brand 在类型层）。
- **运行时机**：跟采集总开关走（暂停 / 退出即停，在途请求 abort、结果丢弃）。开采集先扫一轮（**最近 200 段**），之后每 **10 分钟**一轮；段收口 / 内容写入只是**叫醒**（防抖 5s，让晚到的 UIA / OCR 先落库）。失败按 1 / 2 / 4 … 最长 30 分钟退避，避免同一段每轮重抽。
- **模型**：段向量与名字向量用**信息链自己的**本地 bge 会话（`maxLength 512`，批 1），与图谱那份（256 token）分开——段正文比单条 OCR 长。模型缺失只关向量与名字语义合并（标签 / 双链退化为精确同名复用），不阻塞采集。
- 派生层不写证据表；唯一读证据层的地方是 `MAX(chain_content.id)`（只取水位，不读正文）。

## 4. 与旧数据的关系

- 旧 `events` 是「2 秒采样的 OCR 观察」，**不是**事件点，**不能**改名叫事件。
- 旧 `moments` 是「同 app + 同标题 + 相邻 ≤90s 的分组」，**不是**焦点占用段（没有真实焦点边界、没有输入事件）。
- 新表与旧表并行；旧数据只做「历史观察」检索，不进新段的证据链。

| warm | 7–30 天 | JPEG q85，宽 ≤1920 | 107 KB | 13.8× | 95.2% / 0.840 | 仍可辨认文字区域 |
| cold | 1–6 月 | JPEG q80，宽 ≤1440，打包进当天容器 | 63 KB | 23.5× | 88.5% / 0.717 | 解出后可达 warm 的 3/4 宽度 |
| archive | >6 月 | JPEG q75，宽 ≤1280，打包进当天容器 | 47 KB | 31.5× | 77.0% / 0.600 | 解出后仍能定位到那一刻 |

**两条实测结论（改参数前先看）**：

1. **降 JPEG 质量几乎不掉字**（原分辨率 q85 → q60，相似度 0.959 → 0.924），**缩小宽度掉得多**（1920 → 1280，相似度 0.840 → 0.600）。分层要省字节就压宽度，质量只做微调；别按直觉把 warm 压到 1280。
2. 本机屏幕 1920×1080 @125%，采集管线为了 OCR 把窗口裁剪**放大 2×** 再存，所以 3840 宽的证据图里一半是插值；**宽 1920 恰好是屏幕原生分辨率**（人真正看到的像素）。

容器开销：每条索引约 90 字节（相对 JPEG 可忽略）；**同一批数据重复打包得到同一份字节**（条目按 `shotId` 排序）。参数改动要重跑这套标定并回填本表。

## 5.2 纯键盘输入：采集规则（✅ 已定，写进 `segmenter.ts`）

按「只有鼠标事件才触发采集」，会漏掉**只打字不用鼠标**的场景（写文档、写代码、聊天框里连续输入）。`Alt+Tab` 切窗口不用担心，前台窗口变化钩子能抓到。

漏掉的是**输入本身**：`GetLastInputInfo` 能告诉我们「刚才有输入」，但拿不到输入内容（也不该拿）。

**拍板的规则（D39 / 契约 v0.4；v0.11 修订）**：

- **连续输入期间一张不截**；
- **打字自己停顿也不截**（v0.11）：停顿只补一条 `typing` 事件当锚点；
- **打字被点击 / 滚轮打断时拍一张**（v0.11）：这才是「保住刚敲进去的内容」的时刻；
- 打断也守 2 秒最小间隔（离上一张太近就不拍）；
- 不装键盘钩子（`activity` 输入只表示「有输入」，不含内容）。

实现要点：只有 `kind === 'activity'` 才启动 3 秒计时与「打字中」标记；「打字中」被 `click` / `wheel` 清掉时那一拍就是打断帧。焦点切换、点击、滚轮各有自己的规则，别混成一个「停顿就拍」。

**仍未解决的两件事**（记在这里，不假装已解决）：

1. 打断帧拍的是**打断那一刻**的画面（点击后），不是输入过程中的内容——按拍板人的口径，点击后通常会继续滚动 / 再点 / 再输入，不追求「点前那一帧」。
2. `GetLastInputInfo` 分辨不出「在打字」还是「在按方向键看视频进度」——但按 §5 第 3 条，视频场景不采，这里不额外加判据。

## 6. 最小闭环

> 窗口段 → 事件 → 截图 → 内容 → 能按时间与应用查出段，并从段反查到截图与内容原文；**能按一句话 / 一段时间 / 一个标签或双链名找回那一刻的段**。

**检索入口（v0.9，D46，只读层）**：`searchChainSegments(db, query)` 收 `{ text?, vector?, from?, to?, dayKey?, app?, tag?, link?, minSimilarity?, limit? }`，返 `{ hits, stats }`：

- 每条 `hit` 带 `segment`（段行）、`score`（RRF 分）、`similarity`（余弦，没有向量路为 null）、`matches`（关键词命中几条内容）、`contentIds`（最多 3 条）、`snippet`（命中位置附近的原文摘要）、`tags` / `links` / `counts`（事件 / 截图 / 内容条数）；
- **证据方向**：`contentIds` + `getSegmentDetail(segmentId)` 就能拿到事件、截图（`chain_shot.path` / `container`）与原文，不需要再猜时间；
- 只有过滤条件（没有 text / vector）时按开始时间倒序列出这些段；**什么都没有则空结果**，不会把整库倒出来；
- 结果是纯库函数（没有 IPC / UI）：接 AI 代理或界面时只调它，不重写检索逻辑。

**状态（v0.9）**：真实事件源已接进应用启动；截图是**事件触发现抓**的真实帧；段内文本由**UIA 优先、OCR 兜底**在抓帧后异步读入；证据图**采集即编码 JPEG**，并按 **hot / warm / cold / archive** 四层重编码 / 打包（参数见 §5.1 实测表）；**派生层**（段向量、标签、双链）已接进采集，向量本地算、抽取走 D24 确认门与 D22 预算；**检索入口**可引用段、命中证据、按标签 / 双链过滤。整条「段 → 事件 → 截图 → 内容 → 派生（标签 / 双链 / 向量）→ 检索」在真机上跑通；个人记忆（另一套系统）仍未开工。
