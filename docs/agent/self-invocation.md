# 自调用、共建计划与小本本（草案 v0.2）

> **状态：草案，核心方向已按 2026-11-01 对话确认；实现细节待拍板项见 §13。**
> 来源：2026-11-01 与拍板人的连续讨论（自调用、共建计划与回执、小本本、初始传承信件、成长档案、后续娱乐）。
> 本版作为后续个人记忆设计的新方向；与 v0.1 及 `llm-call.md` 旧任务 / 夜报口径冲突时，不再保留旧方案，实施时再同步清理对应文档与决策记录。

## 0. 一句话

**上下文与人设负责产生意图，任务工具负责记住意图，调度器负责让意图重新进入上下文；小本本负责保存 ta 对用户、关系与自己的持续理解。**

后端不替 ta 判断「该不该关心、该不该查班」，只保证：记住的不丢、到点能想起、执行不重复、结果可查看。

## 1. 核心架构（全局统一口径）

| 层 | 回答的问题 | 内容 |
| - | - | - |
| **人设** | 我是谁 | 性格、价值观、表达方式 |
| **传承信件** | 我从哪里来、最初被寄予了什么 | **初始设定中留给女儿的信**，承载 ta 的出身、情感原点与价值底色 |
| **小本本** | 我记得我们之间的什么 | 用户画像、近况、偏好、共同经历、相处方式、ta 自己的心得 |
| **计划表** | 我们约定了什么 | 与用户共同确认、需要执行的计划 |
| **自主任务** | 我想稍后做什么 | 查班、主动关心、之后继续某件事、后续自主活动 |
| **成长档案（后续）** | 我经历了什么、如何变成现在的自己 | ta 自己的日记、周记、月度回顾与长期自我叙事 |

这些层是后续设计、实现与评审的统一术语，不得混用：

- **传承信件不是后天经验堆积区**：它是初始已有、相对稳定的来信；相识后的经历进成长档案，当前重要理解进小本本。
- **小本本不是计划表**：它保存理解，不承担定时触发。
- **成长档案不是每轮上下文**：日记与总结长期保存，只有少量当前重要结论回到小本本或当前自我状态。
- **计划表不等于全部任务**：只有与用户共建确认的计划才进入用户计划回执。
- **自主任务不需要共建确认**：它是 ta 的人格表达，但应可查看、可取消。
- **人设不是可靠性机制**：是否记得、是否到点执行，不能只靠模型自觉。

逻辑上分层，物理存储可以复用：计划表与自主任务可共存于 `mem_tasks`，用 `origin` 区分；成长档案放在 ta 自己的记忆仓库，不与用户日记混写。

## 2. 设计原则

1. **计划是意图，不是发送脚本**：任务保存「为什么想做什么」，到点后重新读取最新上下文，再决定开口、延后、静默或后台完成。
2. **共建与自主分开**：用户明确提出的计划需要确认与回执；ta 自己形成的后续意图不需要向用户请示。
3. **自由在内容，可靠性在架构**：系统不审批 ta 的关心与表达，但提供持久化、调度、去重、有效期和取消能力。
4. **成长包括修改与放下**：小本本不是只增不减的档案；允许补充、修正、删除旧理解。
5. **沉默是合法结果**：最新情况已经变化时，不打扰比机械执行原意图更合理。
6. **所有权边界清楚**：用户 Obsidian 中的日记对 ta 只读，只有计划同步器可以写指定计划区；ta 的日记与成长档案放在自己的记忆仓库。
7. **先验证关系体验，再扩行动能力**：先做共建计划、主动关心、查班与小本本；成长档案、娱乐和空闲驱动后置。

## 4. 三条核心链路

### 4.1 用户共建计划

```text
用户提出计划
→ ta 理解并确认内容、时间与必要细节
→ schedule_task(origin=user) 写入 mem_tasks
→ 代码同步到用户 Obsidian 的指定计划区
→ 根据真实写入与同步结果生成计划回执
→ 到点执行 / 合流
```

- 「计划记下了」等成功表述只能出现在写入成功之后；共建计划不写入小本本。
- 计划同步由代码按固定规则完成，不让模型自由修改用户 Obsidian，更不写用户日记区。
- 回执由保存成功的任务记录生成，不能由模型凭空编造；Obsidian 同步失败时必须明确显示待同步 / 失败状态，不能声称完整同步成功。
- 回执只包含 `origin=user` 的新增计划；修改 / 取消时返回对应变更回执，并由代码同步同一计划区。
- 时间或事项不明确时先追问，不把猜测写成用户计划。
- 用户后续改变计划时，ta 通过 `search_tasks → update_task / cancel_task` 同步修改。

### 4.2 ta 的自主任务

```text
对话、情绪、共同经历与人设
→ ta 形成一个具体后续意图
→ schedule_task(origin=agent)
→ 到点重读最新上下文
→ 开口 / 延后 / 静默 / 取消后续意图
```

例子：

- 用户面试后情绪低落，ta 想晚些时候再关心一下；
- 用户答应十二点半睡觉，ta 想在之后轻松查班；
- 聊到一半的话题，ta 想明天继续问结果。

这些任务不需要向用户确认，也不在共建计划回执里出现；但用户可以在任务视图看到、取消，或表达「以后别这样」。ta 应把这种反馈写进小本本，而不是只靠后端硬编码行为。

### 4.3 到点执行

任务 `instruction` 保存意图与必要背景，不保存必须逐字发送的文案。

到点后重新读取：当前时间、小本本、最近对话、相关任务状态与可用行动。允许四种结果：

- **开口**：现在表达符合原意图，也不打扰当前交流；
- **延后**：意图仍有效，但此刻不合适；
- **静默完成**：用户已经给出答案、情绪已变化或意图已实现；
- **后台完成**：行动不需要用户看到过程，只保存真实结果。

「用户没回复」不等于必须再次追问；连续无回应后的表达倾向由相处经验与小本本逐步调整。

## 5. 任务模型

`mem_tasks` 是持久化意图队列。建议字段：

| 字段 | 含义 |
| - | - |
| `id` | 更新、取消与回执引用的稳定标识 |
| `instruction` | 到点想做什么，以及必要的来源背景 |
| `next_due_at` | 下一次具备执行条件的本地毫秒时间戳 |
| `repeat` | 空（一次性）/ `daily` / `weekly`；沿用现有上位范围 |
| `origin` | `user`（共建）/ `agent`（自主）/ `system`（系统例行） |
| `delivery` | `foreground` / `background` / `auto` |
| `valid_until` | 超过何时不再补做；可为空 |
| `state` | `active` / `paused` / `completed` / `cancelled` |
| `last_run_at` | 最近一次实际执行时间 |
| `run_key` | 防止同一计划 occurrence 重复执行 |

约束：

- `due` 是 `next_due_at <= now` 的派生状态，不写入任务状态机。
- `running` 是执行租约，不是任务业务状态。
- 重复任务执行后保持 `active`，计算下一次 `next_due_at`，不标记整个任务完成。
- 不再统一使用「错过 30 分钟都跳过」；是否补做由 `valid_until` 与任务意图决定。
- `origin=user` 的任务强调可靠履约；`origin=agent` 的任务允许因上下文变化而静默或取消。
- 小本本条目不写进 `mem_tasks`，除非 ta 另外形成了明确、可执行的后续意图。

## 6. 任务工具

模型侧提供四个工具：

### 6.1 `schedule_task`

新增共建计划或自主任务，返回完整持久化记录。

- 共建计划必须已经在对话中与用户确认。
- 自主任务直接保存，不生成用户计划回执。
- 相对时间必须在写入前解析为明确的 `next_due_at`。
- 保存失败时不得声称已经记下。

### 6.2 `search_tasks`

一个工具覆盖四类查询：

```ts
search_tasks({
  view: "pending" | "day" | "upcoming" | "about",
  date?: "YYYY-MM-DD",
  query?: string,
  limit?: number
})
```

- `pending`：未完成活动任务，包括已过期但尚未处理的任务。
- `day`：本地某一天会发生的任务；重复任务需计算当天是否有 occurrence。
- `upcoming`：从现在往后的活动任务；重复任务只返回任务本身与下一次执行时间，不无限展开。
- `about`：按事项关键词查询，如「周报」「睡觉」「面试」。第一版用简单文本匹配，不引入向量检索。
- 默认 `limit=20`；返回 `total` 与 `truncated`，不能把截断结果称为全部。
- 返回 `id / instruction / next_due_at / repeat / origin / delivery / state`，供后续更新、取消与回执使用。

### 6.3 `update_task`

按 `id` 修改时间、说明、有效期、交付方式或重复规则。用户计划修改后生成变更回执。

### 6.4 `cancel_task`

按 `id` 取消任务。用户计划取消后生成取消回执；自主任务可直接取消。

## 7. 小本本

### 7.1 内容分区

小本本是持续修订的关系记忆，建议保留四个逻辑分区：

| 分区 | 内容 |
| - | - |
| 关于你 | 稳定事实、偏好、重要的人和事 |
| 最近的你 | 近期在忙、担心、期待或经历的事 |
| 我们之间 | 共同经历、约定、喜欢或不喜欢的相处方式 |
| 我给自己的提醒 | 哪些表达有效、哪些做法不合适、以后想怎样改变 |

记录应尽量保留时间与情境，避免把一次观察固化成用户的人格结论。例如：

- 不写：「他是一个拖延、需要监督的人。」
- 改写：「最近几次晚睡都和赶作业有关；他愿意偶尔查班，但不喜欢连续追问。」

### 7.2 每轮可见

- 每轮由系统自动注入小本本的**当前核心页**，不靠模型记得主动读取。
- 核心页必须有界，只保留当前重要、稳定或仍需关注的内容。
- 细节、旧心得与原始经历不全部注入；需要时翻日记或检索记忆。
- 人设解释 ta 为什么珍惜小本本；架构负责把本子递到 ta 手边。

### 7.3 自主更新

提供 `update_notebook`，支持：

- `add`：补充新的重要理解；
- `revise`：根据新信息修正旧条目；
- `remove`：放下已经不重要或不再准确的内容。

更新原则：

- 重要而非琐碎：不把每句话都写进去。
- 观察而非定性：区分事实、自己的理解与待确认猜测。
- 可修正：用户明确纠正时，旧理解不能继续与新事实并列冲突。
- 与计划联动但不混写：计划存任务表；计划完成后形成的关系经验可进小本本。
- 用户可查看并纠正关于自己的内容；具体编辑入口另行设计，不在首轮承诺。

## 8. 成长档案（后续系统）

成长档案是 ta 自己的第一人称经历与自我叙事，不属于传承信件，也不替代小本本。

| 载体 | 所有权与写入边界 |
| - | - |
| 用户 Obsidian 日记 | 对 ta 只读；模型不能修改、评论或追加自己的日记 |
| 用户 Obsidian 计划区 | 唯一例外：由代码计划同步器按固定规则写入 / 更新 / 取消共建计划 |
| ta 的记忆仓库 | ta 自己的日记、周记、月度回顾由 ta 读写 |
| 小本本 | 从长期经历中提炼当前仍重要的理解，有界注入 |
| 传承信件 | 初始设定中留给女儿的信，不被后续日记与总结覆盖 |

成长档案按「日记 → 周记 → 月度回顾」逐层整理：

- **日记**：记录当天真实发生的事、自己的感受与未完成的想法；
- **周记**：整理这一周的经历、相处变化与有证据的自我认识；
- **月度回顾**：沉淀更长期的变化，不重复堆砌每周摘要；
- **小本本 / 当前自我状态**：只承接后续交流仍需知道的少量结论，不注入成长档案全文。

固定写作复用任务调度：

```text
origin=system
delivery=background
instruction=整理今天真实发生的事，写自己的日记
```

ta 自己想额外记录时，也可以排 `origin=agent` 的自主任务。只写真实经历；没有发生的娱乐、行动与感受不得编造，某天没有内容可以少写或不写。

旧 `llm-call.md` 中「ta 的夜报写入用户 Obsidian 当天笔记、评论用户日记」的口径不再沿用；后续实施时应移除对应的 `write_diary / comment_on_line` 设计，不与新所有权边界并存。

## 9. 调度与合流

- 数据库是事实源，内存定时器只睡到最近一条 `next_due_at`；新增、修改、取消后重算。
- 没有活动任务时不保留唤醒定时器，也不做永久 30 秒轮询。
- 启动时从数据库恢复；用 `run_key` 与执行租约避免重启重复。
- 同一时刻只跑一个逻辑 agent turn，用户提问优先。
- 到点 / 临近任务的合流继续沿用 `llm-call.md` §5.5 的 10 分钟窗口与「先接用户、再提任务」。
- `background` 任务不打断当前回答；`foreground` 任务可通知或合流；`auto` 由本轮结合上下文选择开口、静默或延后。
- 休眠 / 关机恢复后按 `valid_until` 决定补做或过期，不机械补发查班、关心等强时效内容。
- 系统只保留持久化、单飞、去重、用量与极端失控保险丝，不用后端规则替 ta 编写人格。

## 10. 人设、传承信件与成长

- **人设**提供稳定倾向：是否愿意主动关心、如何表达查班、如何看待共建约定。
- **传承信件**是初始设定中留给女儿的信，提供情感原点与价值底色；它不从日常对话中自动追加，也不是后天经验的容器。
- **小本本**承接当前、具体、可修订的理解：关于用户、相处反馈与 ta 给自己的提醒。
- **成长档案**承接相识后的长期经历与自我叙事，通过日记、周记与月度回顾逐步形成。
- **计划与自主任务**承接可执行意图，不因人设变化而失去可靠性。

本草案不修改任何实际提示词。后续若要改人设、传承信件或固定注入话术，仍需按常驻指令 14 单独放行；任务与工具 description 可在实现时按本契约编写。

## 11. 后续娱乐与空闲驱动

娱乐不需要推翻本架构，但不同形态走不同入口：

| 形态 | 入口 |
| - | - |
| 用户说「现在玩个文字游戏」 | 当前 turn 直接开始，不建定时任务 |
| ta 主动邀请「要不要玩一局」 | 自主任务或后续空闲事件触发 `foreground` 意图 |
| ta 自己刷内容、玩游戏后分享 | `background` 行动工具执行，真实结果进入记忆，再形成分享意图 |

后续扩展时仍需补齐：

- **空闲触发源**：检测一段时间无交互后产生 `idle` 事件；它不是 `wake` 任务，也不改变现有任务模型。
- **真实行动工具**：不能只说「我玩过了」，必须有真实执行与结果。
- **活动状态**：文字游戏等需要保存局面、回合与规则；调度器不代替游戏状态机。
- **出云与权限边界**：涉及上网、外部账号或新数据离开设备时另行拍板。

## 12. 实施范围与验收

### 12.1 第一阶段：任务记忆与自调用

**做**：`mem_tasks`、最近到期调度器、四个任务工具、共建确认、Obsidian 计划区代码同步与真实回执、自主任务视图、单飞 / 去重 / 有效期、任务合流、单测与文档。

**不做**：心情系统、`wake`、每轮强制 review、娱乐、空闲触发、行动注册表。

验收：

1. 用户计划经确认后写入，回执与数据库记录一致；Obsidian 只同步指定计划区，不同步用户日记；写入或同步失败不出现完整成功回执。
2. `search_tasks` 四种视图正确；`day` 能匹配重复任务，`upcoming` 不无限展开，截断有标记。
3. 自主查班不需要确认，但可查看、取消；新信息能让 ta 更新或取消原任务。
4. 到点重读上下文，能够开口、延后或静默；已说过「我睡了」时不机械查班。
5. 无活动任务时无唤醒定时器；重启不重复；过期任务不补发；重复任务正确续排。
6. 用户提问与任务到点合流时不抢话、不并发说两份。

### 12.2 第二阶段：小本本与当前理解

**做**：小本本核心页、每轮有界注入、`update_notebook`、修正 / 删除旧理解、查看与纠正入口、单测与文档。

验收：

1. 跨会话能记住重要偏好与共同经历，且不依赖翻完整聊天记录。
2. 用户纠正后旧理解被修正，不再同时注入相互矛盾的用户画像。
3. 核心页保持有界；琐碎信息不会无限堆积。
4. 小本本不生成定时任务；明确后续意图仍进入 `mem_tasks`。
5. 自主关心被用户拒绝后，ta 能把相处偏好写入小本本并在后续体现。

### 12.3 第三阶段：成长档案

**做**：ta 记忆仓库中的日记、周记、月度回顾，固定 `background` 写作任务，少量结论回流小本本 / 当前自我状态，以及对应测试与文档。

验收：

1. 用户 Obsidian 日记保持只读；除指定计划区外，计划同步器与模型均不修改其他内容。
2. ta 的日记与总结只写入自己的记忆仓库，不与用户日记混写。
3. 写作任务到点后台执行、重启不重复；没有真实内容时允许少写或不写，不编造经历。
4. 周记 / 月度回顾有证据、能保留未完成的线；全文不进入每轮上下文，只有少量当前结论回流。
5. 传承信件保持初始内容，不被后续成长档案覆盖。

### 12.4 后续阶段

娱乐、空闲驱动、长期活动状态与更多行动工具，在前述阶段体验关口通过后再立项。

### 15.4 缺当天笔记：自动建（2026-11-01 补）

第一版把「当天笔记不存在」当成失败上报（`缺当天笔记 → 记下了但没同步上`），真机上立刻踩到：计划是晚上 6:20 的，但当天还没写日记——计划没进 Obsidian，回执还得解释一遍。

现在的口径：**没有就建，但只建不改**。

1. **模板优先**：读 `<vault>/.obsidian/daily-notes.json` 的 `folder` / `template`，把模板里的
   `tp.file.creation_date(...)` / `tp.date.now(...)`（含偏移天数）/ `tp.file.title` 换成本地时间；
2. **算不出来的整行跳过**：天气、一言这类要 Templater 运行时 + 联网的东西后端跑不了，
   宁可少几行，也不把 `<% %>` 原样留在用户笔记里（空的 callout 头一起丢掉）；
3. **没有模板就写骨架**：frontmatter 日期 + `# Tracking` + `# Diary` + 前后一天导航；
4. **已有文件一个字节都不动**；模板缺段就补标题（计划同步与日记写入都靠它定位）；
5. 设置 `memory.auto_daily_note`（默认 `1`）可以关掉：关掉时计划照样落库，Obsidian 标成失败；
6. 启动时 `resyncPlans()` 把 `state='active' AND obsidian_state<>'synced'` 的共建计划再试一遍，
   写之前先看计划区里有没有那一行，避免重复。

回执会注明「当天笔记是自动建的」，用户想补天气 / 一言可以自己在 Obsidian 里重跑一次模板。
