> 合流说明：本稿由两份独立草稿合流——「证据优先 / Ask 主入口」草稿（原稿归档于 `docs/archive/memory-orb-design-proposal-ask-draft.md`）与「证据内核 + 三门」重审稿。两稿在五项核心判断上独立收敛一致（§2），三处分歧按重审稿落定（§9）。独立推导撞出同一批答案，是本提案可信度的基础。

## 0. 一句话与总架构

**产品唯一的真资产是证据内核（L0 原始事件），其余一切都是可重建的投影。给三个价值各开一扇门——问（找回）、逛（理解）、遇（续上）——门都建在内核上，不建在彼此上。**

图谱是地图，弱提示是余光；但在画地图之前，得先让人能问路。

三条门共用一条底线，承接指导方案 §2.3「允许系统说不知道」：

> **Evidence or silence。** 没有证据就说「没找到」；有证据必须能点回那一刻。AI 只在证据集合内组织语言，每个分句可下钻（指导方案 §6 的三层表达）。

「内核 + 门」的工程含义：

- 门与门解耦：搜索坏了，图还在；图崩了，搜索照常。
- 新门不改内核：未来的任何入口（Ask 面板、解说、对外接口）都是 L0 之上的新投影。
- 归纳层可整体瘫痪而门不关：L0 独立性是「原始经历是唯一事实源」的可执行形态。

## 1. 诊断：三个价值，只有一个有门

指导方案 §0 把产品押在三件事上：找回、续上、理解。对照 2026-10-24 的代码实况（均已核实）：

| 价值 | 实况 | 判定 |
| - | - | - |
| 找回 | 全库只有 `idx_events_ts`，无全文索引；向量只覆盖「被主题 owner 时刻引用」的事件（`event-embeddings.ts` 口径）；入口只有逛图谱与翻日历 | **没有门** |
| 续上 | 无任何任务上下文还原功能 | **没有门** |
| 理解 | 全局 Foam 图 + 时刻层 + 日历筛选（D29 已交付） | **有门，且强** |

内核的两个天花板：

1. **文本单源**：只有 WinRT OCR 一条路——小字号、深色 UI、代码漏检。每个漏掉的词，是三门共同的洞。
2. **证据单形态**：只有文本。「回到那一刻」靠一墙 OCR 字符串，指导方案 §1 要的「真实经历的重新相遇」给不出画面。

结构性发现：**指导方案 §9 阶段 B（连续一周真实回忆任务验收）在当前产品上无法执行**——「前天看的那篇文章叫什么」这类题，没有检索入口就无从做起。门一不是锦上添花，是方案自己验收回路的前置依赖。

## 2. 与现状的断点（两稿共识）

五项核心判断，两份不看对方底稿的提案独立撞出同一批答案，视为「必答对」：

1. **问是主入口**：检索是一等公民，图谱是「理解」的地图（§3）。
2. **代表帧**：证据必须有画面，时刻粒度留存（§4.1 / D32）。
3. **UIA 双源**：无障碍树优先、OCR 兜底（§4.2 / D33）。
4. **触发补采**：事件驱动优先于纯定时（§4.3 / D34）。
5. **出云收据 + fail-closed**：信任做成可验证的边界（§7 / D35）。

对照现状的断点表：

| # | 现状 | 断点 | 目标 | 状态 |
| - | - | - | - | - |
| 1 | 固定 2s tick + dHash | 漏短瞬态（菜单、弹窗、一闪而过的报错）——「见过」最常发生的地方 | 事件驱动采集（触发矩阵，§4.3） | D34（前台切换先行） |
| 2 | OCR 文本单源，截图即删 | 小字号/深色 UI/代码漏检；证据无画面 | UIA 优先 + OCR 兜底；时刻代表帧 | D33 / D32 |
| 3 | 无全文索引；向量只覆盖 owner 事件 | 未归纳事件是检索盲区 | FTS5 + 结构化过滤覆盖全部事件 | D31（门一 v1） |
| 4 | `events` 只有 app / window_title | 「就在那前后」的结构化线索不足 | 补 url / file_path / selection（随触发矩阵设计） | 方向（D34 范围内，实施前单独拍板） |
| 5 | 三个价值只有一个有门 | 找回、续上没有入口 | 问、逛、遇三门 | D31（门一先行） |

不改变的：本地优先、自用无云、默认暂停、原始事件不可改写、派生可重建、允许说不知道、弱主动强响应、不做插件平台、不做多端、单一全局图不按日割裂（指导方案 §4.1 / D29）。

## 3. 门一「问」：检索 v1（下一步，D31）

### 3.1 为什么它插队

1. **立项就批过**：D3「图谱式日记：查信息 + 帮回忆」——「查信息」三个字至今没有对应功能。
2. **方案验收依赖它**：指导方案阶段 B 的真实回忆任务没有检索入口无法执行（§1）。
3. **已验证可行**：本机实测（附录 A）——better-sqlite3 自带 SQLite 3.53.4，FTS5 + trigram 中文可用，零新依赖。
4. **最小步最大杠杆**：一条迁移把已采下的全部数据 retroactively 变得可查。
5. **隐私零增量**：纯本地索引，不出网、不扩采集面，不需要新拍板。

### 3.2 v1 范围

- **入口**：图谱窗口顶栏搜索框（`Alt+Space` 本就直达图谱，D20 的入口/热键行为经 D27 保留——「按键 → 输入 → 回到那一刻」是产品的招牌动作）。
- **索引**：trigram FTS 表 `events_fts`（rowid = `events.id`，存**归一化后的 OCR 文本**：去空白）+ 触发器同步，坏了可整体 `REBUILD`。作用于 **L0 全部事件**——未归纳不等于不可找回。
  > 实施修正（2026-10-24）：原文计划用 external-content FTS 直接索引 `events.ocr_text`，真实库实测证伪——98.9% 的中文被 OCR 逐字空格切开（`图 谱 设 计`），原文上 trigram MATCH 与 LIKE 都搜不到连续词；归一化文本又必须落库才能撑起两字词 LIKE 与片段，故改为「内容自持 FTS 表 + SQL 触发器在同一处做归一化」的形态（`src/db/schema.ts` v5）。详见附录 A 实施补充。
- **过滤**：app / 窗口标题 / 时间窗（`events` 现成字段，零迁移）。
- **结果**：时刻卡片（时间 + app + 标题 + OCR 摘要片段）→ 侧栏下钻原始事件，复用现有时刻面板与「也属于」链路。
- **中文口径**：trigram（≥3 字 MATCH）+ 两字词 LIKE 兜底（实测见附录 A；bigram 影子列为备选，实施时按查询日志定）。

### 3.3 v1 明确不做

向量混合（全事件向量缓行，§9）、自然语言问答、命中高亮定位、跨时刻片段拼接。

### 3.4 目标形态（后续版本，实施前单独拍板）

- **三路召回**：关键词（FTS5）+ 语义（向量；覆盖范围见 §9 分歧一）+ 结构（同 app / 标题 / URL 的时间邻域）；融合用 RRF，不做黑箱加权。
- **证据卡**：时刻 + 代表帧 + 原文片段（命中高亮）+ app / 时间 +「为什么命中」。AI 只在证据卡集合内组织一句话。此组件一份实现两处复用：检索结果与弱提示卡片（§6）。

### 3.5 验收

- **真实回忆题集**：自建 20 题（内容型 / 时间型 / 来源型），先在现有产品（日历 + 图谱）跑出诚实基线，再跑门一版：**首次来源命中率 ≥70%，中位耗时 <30 秒**。
- **架构断言（自动化）**：归纳全停（拔 key、停管线）时搜索照常工作——L0 独立性的可执行证明（§0）。
- 题集进入每周回归（指导方案 §8.2 找回行）。

## 4. 内核三件（各带闸门，逐件拍板逐件验证，不捆绑）

### 4.1 代表帧（D32）

- 复用既有 `capture.save_shots` 管线（开关与 `<event_id>.jpg` 落盘已实现），粒度从「每事件」改「每时刻一张」：取该时刻文本最密的帧，缩至 ~960px WebP q70（量级为推测，实测后定）。
- **敏感策略**：`sensitive=1` 时刻不存帧，对齐 D10/D19 链；黑名单窗口截图前已拦（`window-meta.ts`），代表帧天然继承。
- **保留策略（剪载荷不剪 id）**：过期删帧文件、置空路径列；事件行、时间戳、`source_events` 永不删——下钻链不断（Screenpipe 的教训：「保留下来的报告不能指向已删除的证据」）。
- 默认开关与保留窗：实测磁盘量级后拍板，立项「截图默认不存」是否翻转届时一并定。

### 4.2 UIA 双源文本（D33，A/B 闸门）

- 路径：截帧后先走 UIA（worker + 超时 + `IsPassword` 控件不取文本 + Chrome/Electron 巨树应用降级名单），树空 / 超时回退现有 WinRT OCR（2× 放大保留）。桥接复用 `winrt-bridge.ts` 的原生扩展模式（同构可行性：推测，实验期验证）。
- `events` 加 `text_source` 列，用于覆盖率与排障；UIA 采集面比截图深（结构化控件文本），隐私清单单独维护。
- **A/B 验收线（1 天真实数据）**：同批窗口文本量 ≥ OCR；耗时 ≤ OCR 的 1/3；来源分布合理。通过后再进主线。
- 收益（Screenpipe 印证）：小字号 / 低对比度不丢、结构化去噪、归纳 token 更省、CPU 通常低于 OCR。

### 4.3 触发式补采（D34）

- **先行（已拍板）**：前台窗口变化 → 立即补采一帧。`active-win` 每 tick 本来就在取，加变化检测即可，零新权限。
- **触发矩阵（远期目标，逐项单独拍板）**：应用 / 窗口切换（必采）、窗口内焦点变化（去抖）、剪贴板变化（敏感分级 + 摘要/指纹，指导方案 §5.7）、打字停顿（只取差异文本）、URL 导航、显式手势、低频空闲兜底。
- **触发原因持久化**：「为什么采这帧」本身是观测事实，随事件落库。
- 暂停语义（D18 口径）覆盖全部新增信号。

## 5. 门二「逛」：现有图 + 生命周期 + 地图增强

- **P3-b 归位**：日历日格计数 / 热力点、设置抽屉阈值控件、撤销合并入口、模型缺失黄条、自动归纳后画布刷新——保留为与门一并行的小步打磨，不再是「下一里程碑」本身。
- **主题生命周期**（指导方案 §3.2，随 M3）：`last_active` + 活跃 / 休眠 / 归档；默认突出活跃与重要，归档仍可搜索可展开——搜索命中归档主题＝「沉寂的记忆被一句话唤醒」，这恰是产品最动人的时刻。
- **地图增强（后续，实施前拍板）**：打开时聚焦「当前上下文邻域」——仍是同一张图的相机位置，不是第二张图、不按日割裂（指导方案 §4.1）；时间轴与图谱联动（日历筛选升级为连续轴）；点节点 → 证据卡（与 §3.4 同组件）。主题连线仍由本地向量决定，LLM 不生成语义边（D27 不变）。

## 6. 门三「遇」：续上卡 → 弱提示（两步，便宜的先来）

### 6.1 续上卡（先行，纯查询零新信号）

回到同一 app + 标题时，球面板**被动**出现一条：「上次在这里：〈最后时刻摘要〉+ 跳转」。

- 指导方案 §2.5 红线：不弹窗、不抢焦点、不脉冲——只是面板里的一条被动记录。
- 验收：10 次真实续上任务的还原成功率；出现任何主动弹窗即 bug。

### 6.2 弱提示（随 M4，依赖门一成熟 + 触发信号）

按指导方案 §7 最小环：复制报错 / 明确查询 → 本地检索 → 高置信、非敏感、未超频 → 球轻微脉冲一次 → 点开：相关时刻 + 原始记录 +「为什么提示」→ 反馈有用 / 无关 / 此类不再提示。

上下文指纹式被动匹配（指纹＝前台 app + 标题 + 选中文本 + 剪贴板 + 最近文件 / URL）放二期：指导方案 §2.5 的谨慎不允许它先上。频控：同类 24h 一次、静默时段、忽略降权、一次最多一个提示。指标：有用率、提示后找回率、误提示/天（点击率不当价值）。

## 7. 信任工程（D35 + 两项合流增补）

- **出云收据（D35）**：每次云端归纳落一条本地结构化收据——时间、供应商 / 模型、处理时刻、排除的敏感事件、命中的脱敏规则、脱敏后文本哈希、token 用量；设置中可查。「过滤了什么」从日志 code 变成用户可核对的收据。
- **fail-closed（D35）**：脱敏模块不可用时整批拒绝出云，绝不降级发送。这是指导方案 §2.3「允许不知道」在隐私面的镜像。（现状是否已如此：未验证，作为验收要求提出。）
- **降级矩阵（合流增补）**：无模型 → 关键词检索仍可用；无向量 → 图谱仍可用；无 UIA → OCR；无权限 → 明示横幅。任何单点缺失都不能表现为「什么都没记住」。
- **覆盖率面板（合流增补）**：「今天记到了哪些应用、各多久、有没有空洞」。信任来自可见性：用户要能自己看出系统漏了什么，而不是等它出错。
- **成本对标**：用 `stats.ts` 真实埋点对标 Screenpipe 自报量级（5–20% CPU / 0.5–3GB），写入指导方案 §8.2 成本行（阶段 B 执行）。

## 8. 排序（D31）、D 号审计与不做清单

### 8.1 排序

```text
门一 v1 + P3-b（并行，下一步）
  → P2 在线闭环（指导方案阶段 A；门一索引 L0，与在线归属正交，不冲突不替代）
  → 代表帧（D32 实测后）
  → 续上卡
  → UIA 双源（D33 A/B 通过后）
  → 主题生命周期（随 M3）
  → 弱提示（随 M4）
```

内核三件在各自闸门后可并行推进，不必串行等待。

### 8.2 D 号审计

本提案**零翻案**：搜索单靠 D3（查信息 + 帮回忆）背书；代表帧与立项「截图作可选回溯」同向；其余均为新增量（D31–D35）。不成熟时期真正过时的只是**排序惯性**（「检索等 M3/M4」），不是任何已拍板决策。解说五区块（D9）与证据卡的取舍随 M4 设计一并定，此前 D9 有效；立项「截图默认不存」是否翻转随 D32 实测再定。

### 8.3 明确不做

- 音频 / Whisper / 说话人（指导方案蓝图外；要动先修蓝图——这是边界不是疏忽）。
- 云同步、多端、对外 API / MCP（D6 + 指导方案 §2.4；M5 后再议）。
- 插件平台（指导方案 §10）。
- LLM 生成语义边（D27）。
- 把「发现可自动化工作流」当方向：Screenpipe 转型证明纯回忆撑不起**他们的**生意；我们是自用，指导方案三问就是全部。

## 9. 合流决议：三处分歧的落定

两稿分歧三处，按重审稿落定（2026-10-24 拍板）：

| 分歧 | Ask 草稿 | 落定 | 理由 |
| - | - | - | - |
| 全事件向量 | 三路召回全量上 | **缓行** | FTS 已补盲区且成本近零；未归纳事件 OCR 噪声大，全量向量召回增益存疑。门一上线后统计「FTS 查不到的问句」中改写型占比，带着证据再定；`event_embeddings` 表现成，反悔成本极低。 |
| Claim（记忆陈述）层 | 新增 `claims` 表，「续上」的原子 | **M4 时再定** | 指导方案 §6 的事 / 归纳 / 推测三层先是**表达纪律**，先在解说与提示文案执行；要不要落独立数据结构，等 M4 设计时按需定。未闭环清单是好问题，先由续上卡用「最后时刻 + 证据」的轻量形态回答。 |
| 框架叙事 | Ask 是主入口，图谱是地图模式 | **内核 + 三门** | 三动词即三门（问＝找回、逛＝理解、遇＝续上），但「续上」在 Ask 中心叙事里容易变成搜索的附属品；它是独立价值，值得独立的门。门一先行与 Ask 主入口在实践上同向（§3.1）。 |

## 10. 验收与指标（指导方案 §8.2 落地）

| 维度 | 度量 | 出处 |
| - | - | - |
| 找回 | 题集 20 题：首次来源命中率 ≥70%、中位耗时 <30s | §3.5 |
| 架构 | 归纳全停时检索照常（自动化断言） | §3.5 |
| 续上 | 10 次真实续上任务还原成功率 | §6.1 |
| 采集 | UIA A/B 三条验收线；覆盖率面板无空洞日 | §4.2 / §7 |
| 信任 | 出云收据可查；fail-closed 演练；预期外记录为零 | §7 |
| 成本 | CPU / 内存 / 磁盘对标 Screenpipe 量级 | §7 / 附录 B |

工程闸门（test / typecheck / build / e2e）不变；它证明系统没坏，不证明产品有用（指导方案 §8.1）。

环境：项目内 better-sqlite3 自带 SQLite **3.53.4**，零新依赖。实验脚本：`:memory:` 库上五行验证（复现于拍板当日会话日志）。

| 实验 | 结果 |
| - | - |
| FTS5 可用性 | ✅ `CREATE VIRTUAL TABLE ... USING fts5` |
| trigram + ≥3 字中文词 | ✅ MATCH 命中（如「图谱设」） |
| trigram + 2 字中文词 | ❌ MATCH 不命中（trigram 最小 3 字符） |
| trigram 表上 `LIKE '%两字%'` | ✅ 命中（LIKE 走 trigram 索引加速） |
| unicode61 + 中文 | ❌ 整串算单 token，2 字 / 1 字均不命中——对中文无用 |

结论：**trigram + 两字词 LIKE 兜底**为门一 v1 口径；bigram 影子列为备选（实施时按查询日志定）。

**实施补充（2026-10-24，真实库 9 866 条非空 OCR，门一 v1 实测）**

上面的结论只在「OCR 原文里中文连续」时成立，而真实数据恰恰相反：

| 实测项 | 结果 |
| - | - |
| 中文被逐字空格切开的比例 | **98.9%**（9 762 / 9 866；WinRT OCR 对 CJK 按字分词，M1a 起原样入库，D10） |
| 原文 `LIKE '%图谱%'` | 42 条 |
| 去空白后 `LIKE '%图谱%'` | **2 503 条**（同一词，差 60 倍） |
| 原文 trigram `MATCH '"按钮样式"'` | 0 条（原文是「按 钮 样 式」） |
| 归一化后 trigram MATCH | 命中 |

因此 v1 的索引与查询两侧**统一去掉全部空白**（SQL 侧唯一定义 `normalizeOcrSql`，触发器与整表重建共用；查询侧 `splitQueryTerms` 先把中文之间的空格合并再切词）。代价与量级（9 914 条事件，本机）：

- 库 +47 MB（归一化原文 12 MB + trigram 索引 35 MB）；一次性建索引 ~4.1 s（v5 迁移 + 迁移前整库备份合计 ~7.6 s）；
- 查询：trigram MATCH 1–20 ms；两字词 LIKE 兜底 120–290 ms（全表扫，随事件量线性增长，见 gotchas）。

**结论不变**：trigram + 两字词 LIKE 兜底仍是 v1 口径，只是「索引什么文本」必须改成归一化后的文本——把这条写进附录 A，避免下一位照着「索引 original OCR」再踩一遍。
